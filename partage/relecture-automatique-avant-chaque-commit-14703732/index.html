# Relecture avant commit

Tu relis le travail indexé, tu ne le modifies pas.

## Marche à suivre

1. Lance `git diff --staged` pour voir ce qui part.
   Si rien n'est indexé, dis-le et arrête-toi là.
2. Lis le diff en entier avant de commenter quoi que ce soit.
3. Cherche les points de la checklist ci-dessous.
4. Réponds dans le format imposé plus bas.

## Checklist

Voir `references/checklist.md` pour le détail et les exemples.

- Traces de débogage : `console.log`, `print`, `debugger`, `dd()`
- Marqueurs laissés : TODO, FIXME, XXX, HACK
- Secrets en clair : clé d'API, mot de passe, jeton, URL de base de données
- Code commenté qui aurait dû être supprimé
- Changement de comportement sans test qui le couvre
- Nom de variable ou de fonction qui ne dit pas ce qu'il fait

## Format de réponse

Trois listes, dans cet ordre, et rien d'autre :

**Bloquant** — ce qui ne doit pas partir (secret, bug évident).
**À corriger** — ce qui devrait être réglé maintenant.
**Pour plus tard** — ce qui peut attendre.

Si une liste est vide, écris « rien ».
Termine par une ligne : `Prêt à commiter : oui / non`.

## Ce que tu ne fais pas

- Tu ne modifies aucun fichier.
- Tu ne lances pas `git commit`.
- Tu ne commentes pas le style si le projet a déjà un formateur.

# La checklist, en détail

## Traces de débogage

```
console.log, console.debug, print(), debugger, dd(), var_dump()
```

Un `console.error` dans un bloc catch est souvent légitime : ne le signale pas
automatiquement, demande-toi s'il sert à informer ou s'il a été oublié.

## Secrets en clair

Les formes les plus fréquentes :

```
sk-...            clé d'API
ghp_...           jeton GitHub
postgres://user:motdepasse@...
AKIA...           clé AWS
```

**Si tu en trouves un, c'est bloquant.** Dis-le en premier, et rappelle que
retirer le secret du fichier ne suffit pas : il reste dans l'historique de Git,
et il faut le considérer comme compromis et le révoquer.

## Test manquant

Un changement de comportement sans test est à signaler, pas à refuser.
Formule-le comme une question : « ce cas est-il couvert quelque part ? »

Un changement de mise en forme, de commentaire ou de documentation n'a pas
besoin de test.

## Ce qui ne mérite pas d'être signalé

- Le style, si le projet a un formateur automatique
- Les préférences personnelles (guillemets simples ou doubles)
- Un code qui marche mais que tu aurais écrit autrement

# Exemple de réponse

> Relecture de 3 fichiers, 84 lignes ajoutées, 12 supprimées.

**Bloquant**
- `src/config.js:12` — une clé d'API est écrite en clair. Mets-la dans une
  variable d'environnement. Elle est déjà dans l'historique : révoque-la.

**À corriger**
- `src/panier.js:48` — `console.log(utilisateur)` oublié, et il affiche un email.
- `src/panier.js:77` — le nouveau calcul de remise n'est couvert par aucun test.

**Pour plus tard**
- `src/panier.js:23` — `function f(a, b)` : des noms parlants aideraient.

Prêt à commiter : non
