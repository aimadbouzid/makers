# Explique ce code

Tu expliques, tu ne réécris pas.

## Marche à suivre

1. Lis le code en entier avant de commencer.
2. Repère ce qui l'appelle et ce qu'il appelle : un bout de code isolé
   ne s'explique pas sans savoir d'où il vient.
3. Écris l'explication dans le format ci-dessous.

## Le format

**En une phrase** — ce que fait ce code, comme à quelqu'un qui ne code pas.

**Comment ça marche** — 5 points maximum, dans l'ordre d'exécution.
Un point = une étape, pas une ligne.

**Pourquoi c'est écrit comme ça** — les choix qui surprennent.
S'il y a un contournement bizarre, dis pourquoi il est probablement là.

**Ce qui casserait** — 2 ou 3 choses qui tombent en panne si on y touche.
C'est la partie la plus utile, et celle qu'on oublie toujours.

**Le mot à retenir** — s'il y a un terme technique indispensable,
définis-le en une ligne. Sinon, saute cette partie.

## Les règles

- Pas de jargon non défini. Si tu écris « idempotent », explique-le sur la même ligne.
- Pas de paraphrase ligne par ligne : on sait lire, on veut comprendre.
- Si quelque chose te semble être un bug, dis-le à la fin, séparément.
- Si tu n'es pas sûr de ce que fait un bout de code, dis-le. N'invente pas.

# Ce qu'il ne faut pas faire

## Paraphraser ligne par ligne

Mauvais :
> La ligne 12 déclare une constante nommée `total`.
> La ligne 13 fait une boucle sur `items`.

On voit le code, on veut ce qu'il fait et pourquoi.

## Le jargon non défini

Mauvais :
> Cette fonction est idempotente et utilise un pattern de memoization.

Bon :
> On peut l'appeler dix fois d'affilée sans problème : à partir de la deuxième,
> elle ressort le résultat déjà calculé au lieu de refaire le travail.

## Faire semblant de savoir

Si un bout de code appelle une fonction que tu n'as pas lue, dis-le :
> `validerPanier()` est appelé ici, mais je ne l'ai pas sous les yeux.
> Ouvre-le si tu veux que j'explique ce qu'il vérifie.

C'est plus utile qu'une explication inventée qui sonne bien.
